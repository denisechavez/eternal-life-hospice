# Public Form Submission Routing Verification

**Checked:** 2026-08-26  
**Scope:** Public Eternal Life Hospice form markup, the reachable Google-hosted production domain, the reachable Netlify hostname, and the repository’s Netlify submission handler.  
**Safety:** All live POST probes were synthetic routing checks. They contained only a form name and a deliberately populated honeypot field; no name, email address, phone number, clinical detail, patient identifier, file, or other PHI was submitted.

## Executive conclusion — migration blocker

The public domain, `https://eternallifehospice.com`, is served by Google Frontend at `34.111.179.208`, not Netlify. Its public form pages retain Netlify-form markup, but that markup is inert on Google hosting.

Every tested public POST reached the Google-hosted preview server. It returned HTTP 200 with a “Preview mode” page stating that submissions are not stored. The page JavaScript treats that HTTP 200 as success, so a referrer can see a confirmation even though the Google-hosted service has not routed the submission to Netlify, Resend, or an identified team inbox.

**Do not migrate or repoint the public site until a production form destination, team notification recipient, and end-to-end non-PHI acceptance check are explicitly configured and verified.**

## Live evidence

### Google-hosted public domain

- `https://eternallifehospice.com/`, `/refer`, `/careers`, and `/care-brief.html` returned `server: Google Frontend`; the domain resolved to `34.111.179.208`.
- The public homepage, referral page, and careers page all use relative `fetch("/")` POSTs. The chat callback script also uses `fetch("/")`.
- A synthetic POST to `/`, `/refer`, and `/care-brief/` returned HTTP 200 and the same “Preview mode” response. The response explicitly says form submissions are only recorded on the live site.
- That response is generated by `website/devserver.py`: its `do_POST` implementation consumes the body and returns a 200 preview page without storing or forwarding anything.
- The homepage calls its success UI on both fulfilled and rejected requests. The referral, careers, and direct Care Brief pages show their success UI for any `r.ok` response. Consequently, the Google handler’s 200 response creates a false confirmation.
- The Google-hosted public domain returned 404 for `/.netlify/functions/submission-created` and the other checked Netlify/API paths; it does not expose the Netlify function endpoint.

### Netlify hostname

`https://eternallifehospice.netlify.app` is reachable and is served by Netlify. Its deployed HTML is not byte-identical to the repository markup, but it recognizes current form names:

- An unknown synthetic form name returned Netlify 404.
- Synthetic, honeypot-marked POSTs using `elh-physician` and `elh-care-brief-signup` returned Netlify 200.
- The saved Netlify Forms screenshot in `attached_assets/Active_forms_1782739920950.jpeg` shows form detection enabled and these older active forms: `elh-chat-callback`, `elh-coordinator`, `elh-casemanager`, `elh-physician`, `elh-family`, and `elh-careers`.

This establishes that the Netlify hostname has a form-recognition path that the Google-hosted public domain does not. It does **not** prove which team inbox receives Netlify Forms notifications or whether every current form name is enabled in the current Netlify deploy.

## Netlify delivery path in the repository

When a matching site is deployed through Netlify:

1. Netlify Forms receives and stores the submission.
2. Netlify invokes `netlify/functions/submission-created.js` after a verified submission.
3. The handler sends an acknowledgement through Resend for eligible forms with a valid email address: `elh-family`, `elh-casemanager`, `elh-careers`, `elh-physician`, `elh-care-brief-signup`, and `elh-voice`.
4. `elh-chat-callback` is the one code-controlled internal routing path: the handler sends its callback details through Resend to `referral@eternallifehospice.com` and does not auto-reply to the requester.

The handler cannot run for Google-hosted posts because the public Google deployment does not include the Netlify function runtime. A source comment on `/refer` says the Netlify UI notification for `elh-physician` was configured to `info@eternallifehospice.com`, but this was not independently verified in the Netlify dashboard and must not be treated as current operational proof.

## Required decisions before consolidation

1. Select the production form processor: Netlify Forms plus its configured notifications, or a deliberately implemented Google-hosted handler. Do not rely on `data-netlify` outside Netlify.
2. Confirm one monitored internal destination for each public form in the active platform dashboard, including the referral flow and careers uploads.
3. Deploy the selected production code to the domain that DNS actually serves.
4. Run one documented end-to-end test with a designated non-PHI test record and confirm both the team notification and requester acknowledgement behavior. Remove the resulting test submission according to the selected platform’s retention process.
5. Change the client success logic so it only confirms receipt after the selected processor confirms persistence/notification, and presents the 24/7 phone fallback on failure.

## Verification limits

No production dashboard credentials, notification settings, mailbox delivery logs, or platform retention settings were inspected. This report therefore distinguishes source-level routing from directly observed HTTP behavior and does not claim that an unverified notification recipient is active.
