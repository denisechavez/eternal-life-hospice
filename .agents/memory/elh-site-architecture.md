# Eternal Life Hospice static site (website/elh-preview/)

## Stylesheet linkage is NOT uniform — check before any global style change
- Most inner pages (404, careers, volunteer, all `hospice-*.html`, all `resources/*.html`) link `assets/elh.css`.
- BUT `index.html` (homepage) AND `resources.html` are **inline-CSS only** — they do NOT link elh.css; their styles live in their own `<style>` block with their own `:root`.
- **Why it matters:** Editing elh.css does NOT affect index.html or resources.html. Any shared style change (header, vars, etc.) must be duplicated into those two pages' inline `<style>` blocks separately, or they silently render unstyled/stale. This caused rework — resources.html's new header was unstyled until its inline CSS was patched.
- **How to apply:** Before changing any "site-wide" CSS, grep each target page for `elh.css`; for inline-only pages, edit their `<style>` directly.

## After editing shared elh.css, bump the `?v=` cache version in LOCKSTEP across every referencing file
- elh.css is linked with a `?v=<timestamp>` query on most pages. `_headers` caches `/assets/*` 1 day, so without a version bump the live site serves stale CSS for up to a day after a change.
- **Trap:** linkage is not uniform even for the version — the ~23 top-level pages carried `elh.css?v=<ts>` but the `resources/*` article pages were VERSIONLESS (`../assets/elh.css`). A blanket bump must (a) replace the old `?v=` on versioned pages AND (b) add a `?v=` to the versionless ones, leaving zero versionless refs.
- **How to apply:** pick one new version string and apply to all refs in one pass: `rg -l 'elh\.css\?v=OLD' | xargs sed -i 's/elh.css?v=OLD/elh.css?v=NEW/g'` then `rg -l 'assets/elh\.css"' | xargs sed -i 's#assets/elh.css"#assets/elh.css?v=NEW"#g'`. Verify: `rg -No 'elh\.css\?v=[0-9]+'` shows ONE version, and `rg -l 'assets/elh\.css"'` returns nothing. (chat.js only mentions elh.css in a comment — not a real link.)

- `.hero--photo` (+ `::after` dark overlay + inline `background-image`) is the standard resource-article hero, used by many pages. To change a single page's hero, scope the change to that page only; never edit the shared `.hero--photo` rule (it would restyle every photographic hero).
- **comfort-therapies heart hero — FINAL state (user is VERY particular; cycled through blurred-fill → tight crop → bigger heart in blurred-fill → full contained image → and ultimately back to the STANDARD format).** Final landing decision: the hero must match every other resource article hero = full-bleed `<section class="hero hero--photo" style="background-image:url('../assets/img/comfort-therapies-hero.jpg')">` with `.kicker`/`h1`/`p` overlaid (dark gradient via `.hero--photo::after`). Consistency with sibling pages won over the "show entire image" idea, so cover-cropping is accepted here. Source image = the full heart photo resized to 1600x1356 (`comfort-therapies.jpg` / `-hero.jpg`, byte-identical, also the resources.html card thumbnail). The heart is centered in the photo so center-cover shows it. **Keep the hero STRUCTURE identical to siblings (no contained `<img>`, still `class="hero hero--photo"`).** BUT the shared `.hero--photo::after` overlay (rgba(40,24,56) .60/.66/.84) was too dark and hid the heart — so this page has a small page-scoped `<style>` block (in its `<head>`) targeting `#ctHero` (the hero now carries `id="ctHero"`): lighter overlay gradient (.30/.34/.60) and `background-position`. (NOTE: a stronger kicker/h1/p text-shadow was added then REMOVED — user asked to remove the hero drop shadow, so it's now `text-shadow:none`; legibility relies on the overlay alone. Don't reintroduce a text-shadow here.) This is page-local (ID specificity beats the shared class) — the canonical way to do one-off hero visibility tweaks: page id + scoped style, never mutate the shared `.hero--photo` rule. Fix without side bars = give #ctHero more height (`min-height:clamp(420px,56vh,560px)` + flex column center) so cover reveals more of the photo (whole heart + hand). To frame more/less, adjust #ctHero `min-height` and `background-position` Y — NOT background-size (shrinking it below cover introduces plum side bars, which the user dislikes).

## Shared header (wordmark + hamburger nav)
- Markup uses `<header id="hdr">` + `.hdr-in` > `.hdr-logo` (two swap imgs `assets/img/elh-logo-h-cream.png` / `elh-logo-h-plum.png` = the FULL horizontal logo + a now-hidden `.hdr-wordmark`), `nav`, `.hdr-cta` phone pill, `.menu-btn`.
- **The header logo is the brand's full HORIZONTAL lockup image (mark + "Eternal / LIFE HOSPICE" logotype), NOT a mark + CSS text.** The old `.hdr-wordmark` text span is still in markup but set `display:none` in all 3 CSS places — the image carries the name. Don't "restore" the CSS wordmark; the user explicitly wanted the real logotype font from the logo file. `.hdr-logo img.s{height:46px}`.
- Behavior JS: `assets/header.js` (scroll→`.scrolled`, hamburger→`.nav-open`, close on outside-click + nav-link click). Faithfully mirrors homepage inline JS — keep at parity; homepage has no Esc/aria-controls, so don't add them to inner pages only.
- Inner pages use `position:sticky` (avoids hero overlap); homepage uses `position:fixed`. Accepted divergence.
- Path variants: top-level pages use `index.html#...` / `assets/...`; `resources/*` subpages use `../index.html#...` / `../assets/...`.
- Responsive parity rule that's easy to forget: `@media(max-width:980px){.hdr-cta{display:none}}` — must exist in elh.css AND resources.html inline AND index.html.
- `family-guide.html` and `ELH_Family_Guide_Interactive.html` are standalone docs with NO header by design — leave them alone.

## Editing index.html / resources.html
- These have long single-line body HTML — use python/grep, not line-based read/edit, to extract or replace blocks (e.g. `re.sub(r'<header\b.*?</header>', ..., flags=DOTALL)`).

## Netlify forms — file uploads
- Lead forms submit via AJAX urlencoded, but **any form with a file upload must use `enctype="multipart/form-data"` and submit `new FormData(form)` with no manual Content-Type** — the urlencoded path silently drops the file.
- **Why:** A job-application/upload funnel must never show false success. Gate the success UI on `response.ok`; on failure keep the form, re-enable the button, and show a phone fallback.

The legacy generic `footer{}` / `.ftag` / `.fcontact` rules in elh.css are dead but harmless; the `#site-footer`-scoped block (appended later) wins on specificity+order.

## QR codes (point to eternallifehospice.com)
- A QR placed on a DARK surface must carry its own light backing or it won't scan. The footer sits on `--deep` (dark plum), so the footer QR uses the **cream** variant (`assets/img/qr-cream.png` = plum modules on cream) — NOT the transparent/plum variant, which would be dark-on-dark and unscannable. **Why:** scanners need module/background contrast; "transparent for dark backgrounds" is wrong for QR. Same reasoning anywhere a QR lands on a colored surface.
- QR source PNGs are generated with high error-correction (level H) so the centered ELH infinity logo doesn't break decoding. If you regenerate or resize, keep EC level H and re-decode to confirm before shipping (see family-guide memory for the puppeteer+jsQR verify pattern).
- Placements: footer brand column on all 31 footer pages (`.foot-qr`, CSS in the same 3 places as header/footer — elh.css + index inline + resources.html inline), a `.res-qr-card` callout on resources.html, and a self-contained `.guide-qr` block on the family-guide colophon leaf. `family-guide.html` carries `.guide-qr`, not `.foot-qr` (it has no site footer). ## Internal link audits — two false-positive traps
- A naive href/src audit over this site WILL falsely flag two link styles that are actually valid: (1) **absolute paths** like `/assets/chat.js`, `/assets/img/*` resolve to the Netlify **publish root** (= `website/elh-preview/`), not the OS filesystem root — strip the leading `/` and resolve from the site root. (2) **query-string links** like `index.html?lead=physician#leadcap` are valid (homepage `URLSearchParams('lead')` handler) — split off `?...` before the existence check. After accounting for both, the site has zero broken internal links.

After any blanket bump, REVERT these to originals (13/12/15/11/11/13/11/9.5; .map-label 9.5). Verify on `hospice-ventura-and-los-angeles-county-ca.html`.

## Local preview MUST use `serve` (clean URLs), not python http.server
- Netlify serves pretty/clean URLs (`/family-guide` → `family-guide.html`). The dev preview iframe rewrites in-page links to that extensionless form when clicked.
- **Why it matters:** if port 5000 (what the preview uses) is served by `python3 -m http.server`, every extensionless click 404s and the whole site looks like "all links broken" — but it's purely the dev server, links are fine in a real browser/Netlify. `serve` (npm) has cleanUrls on by default and resolves both `/family-guide` and `/family-guide.html`, matching production.
- **How to apply:** keep ONE webview workflow on port 5000 running `serve website/elh-preview -p 5000 --no-clipboard`. If two workflows both grab 5000, python can win the port — remove the python one. Verify with `curl -o/dev/null -w '%{http_code}' localhost:5000/family-guide` → expect 200, not 404.

## "Image looks blank / shows the old version" reports are almost always client cache or un-republished Netlify, not code
- Repeatedly the user reports a hero/card image as blank or stale that renders correctly in the local preview (verified via app_preview screenshot + assets returning HTTP 200). The file and reference are fine; the gap is the user's browser cache or the live Netlify site not yet redeployed from GitHub.
- **How to apply:** before editing anything, screenshot the page locally and curl the asset for a 200. If both pass, the fix is a hard-refresh or a republish — not a code change. `_headers` sets 1-day cache on `/assets/*`, so swapped images at the same filename can serve stale for up to a day.

## In-page anchor stops on index.html need a corrective re-scroll (lazy-load shift)
- index.html is long with many `loading="lazy"` images, so a fresh load that jumps to a `#hash` (e.g. cross-page footer/nav links like `index.html#founder`, `#standard`, `#medicare`, `#clinical-mobile`) lands TOO HIGH — images above the target size in after the jump and push the target down, leaving the prior section in view.
- Fix already in place: two on-load IIFEs near the end of the homepage script — one specific to `#leadcap`/`?lead=`, plus a GENERAL handler that re-runs `scrollIntoView({block:'start'})` at staggered timeouts (~80–1600ms) for any valid in-page `#hash`. `scroll-margin-top` (sections 90px, `#clinical-mobile` div 84px; header is 74px) supplies the offset so it stops just below the sticky header.
- **Why:** without the corrective re-scroll only `#leadcap` worked; all other footer/menu anchors stopped on the wrong section. Keep the general handler; don't assume native hash-jump alone is enough on this image-heavy page.

## Never use broad document-level anchor-click interceptors
- A global `document.addEventListener('click', a=e.target.closest('a[href^="/"]'); e.preventDefault();...)` that only *acts* on some links but `preventDefault()`s ALL matched ones silently kills every other root-relative link (made worse when the preview rewrites links to root-relative form).
- **How to apply:** scope the selector to exactly the intended links (e.g. `a[href^="/hospice-care-"]`) and only call `preventDefault()` inside the matched branch. The homepage `#coverage` city-scroll handler is the one legitimate case.

## Hero photos from portrait sources — coherent crop vs blurred-fill (decided)
- For wide-short hero/card containers fed by a PORTRAIT photo, the "blurred-fill framing" trick (sharp center crop centered over a blurred+extended copy of itself) ONLY reads well with HEAVY blur (~0x24+). With LIGHT blur the legible background looks like a pasted, misaligned DUPLICATE box. So if the user wants the scene to look sharp/clear, DON'T light-blur the wings — switch to a SINGLE coherent landscape crop of the real photo (the room's own walls frame it) and accept normal `center/cover` top/bottom cropping on extreme aspect ratios.
- **Adding a person to a real photo:** generateImage is text-only (no inpaint/edit). To add someone, generate a faceless cutout (`removeBackground:true`, back/side view, neutral attire), then composite with `magick` adding a horizontal `-motion-blur` + a soft blurred-ellipse contact shadow. Motion blur both says "busy office" and hides paste seams; back view = no face by construction. Composite onto the coherent crop, then view before applying.
- **Why:** the careers hero went heavy-blur → user wanted "less blur + a person"; light-blur wings exposed the duplicate-box artifact, so the coherent-crop + motion-blurred walking cutout was the fix.

## SEO launch-lock: clean pretty URLs are the canonical form
- Hosting = Netlify pretty URLs (`netlify.toml` `publish="."`, no build); the dev preview workflow uses `serve` which ALSO does clean URLs + 301s `.html`→clean. So `/slug` serves `slug.html` and `/slug.html` 301-redirects to `/slug`.

## Mobile horizontal-shift lesson (July 2026)
Rule: `body{overflow-x:hidden}` alone does NOT stop sideways panning on iOS — `html{overflow-x:clip}` is required at the document root (now applied site-wide: index/resources/family-guide inline CSS + shared elh.css).
**Why:** the page shifted left/right on swipe. Root causes were a lead-form grid blowout (1fr columns can't shrink below inputs' intrinsic min-width → need min-width:0 on grid items and form controls) and a nowrap span on family-guide.
**How to apply:** to find offenders, inject a JS probe (enumerate elements with rect.right > clientWidth that have no overflow-clipping ancestor) and run headless chromium --dump-dom at --window-size=390. Verify scrollWidth == clientWidth on every page after any layout change.

## Hero (homepage) vertical spacing is centering-driven — pad the flex child, not the container
- `.hero{min-height:94vh;display:flex;align-items:center}` with `.hero-content` as the flex child. On desktop the content is shorter than 94vh, so it sits centered with slack top & bottom (comfortable gaps). On narrow/mobile the content is TALLER than 94vh, so it overflows: no slack, content goes flush to the top (eyebrow jams the credential/trust bar) AND the bottom (hero-pills jam the fold / "edge of the page").
- **Fix pattern:** put symmetric vertical padding on `.hero-content` (e.g. `padding:3rem 2.5rem`). Vertical centering ABSORBS it on desktop (measured gap unchanged) but it becomes real breathing room on narrow/mobile (0 → ~48px both ends). So this is the way to fix mobile-only hero crowding WITHOUT altering the desktop layout — don't add a mobile-only media query for it, and don't pad `.hero` itself (that would shift desktop).
- **Why:** verified with headless chromium at 1366/820/390 — desk gapEbToStrip stayed 90px before & after; mobile went 0→48px top and ~0→48px pills-to-fold. Diagnose hero spacing complaints by measuring at multiple widths first; "too close to the trust bar" = top flush, "pills too close to the edge" = bottom/fold flush, both the same root cause.
- CSS pitfall (fixed July 2026): `.sec{padding:3rem 0}` appears after `.wrap{padding:0 1.6rem}` at equal specificity, so any element with BOTH classes lost horizontal padding (flush-left text on mobile article pages). Guard rule `.article.wrap{padding-left/right:1.6rem}` now sits after `.sec` in elh.css — keep it when editing, and never rely on `.wrap` padding for elements that also carry `.sec`.

- Footer icon-spacing trap (fixed July 13 2026): `#site-footer .foot-col a{display:block}` (1,1,1) out-specifies `#site-footer .fc-line{display:flex}` (1,1,0), killing the icon gap on every elh.css page + resources.html inline copy; index inline copy used class-only selectors so it looked fine. Fix = add `#site-footer .foot-col a.fc-line` to the flex rule. When adding footer contact rows, keep that higher-specificity selector.
